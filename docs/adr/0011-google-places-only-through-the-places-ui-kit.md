# Google places are shown only through Google's Places UI Kit and kept as place IDs

Members can browse Google Maps places (a mehendi artist near Malviya Nagar, a tent house in Pune) in a full-screen Google places sheet built from Google's Places UI Kit, Essentials tier (`gmp-place-search` and `gmp-place-details-compact`). Google's own map sits beside the list inside the sheet and shows where each result is, so the sheet reads like the "Places" box on a Google Search results page: the list on the left, the map on the right, stacked on phones. Google's own components draw every name, address, rating, photo, the map and the attribution, themed with the `--gmp-mat-*` CSS custom properties so the sheet matches our tokens. When a Member saves a place, Utsavvy keeps only Google's place ID, the Member's own note, who saved it and when, as a Google place on the Canvas. Opening it again loads fresh details by place ID inside the sheet; "Open in Google Maps" hands off to Google Maps. No Google content reaches our database, a Vendor record, a Canvas card, a Marker, the Chat or the Assistant. Decided with Sah-Nikhil on 2026-10-21 as MUST slice S20; Google's map beside the list added with him on 2026-10-22.

## Why this way

Google lets other websites show its places data in exactly one way that also lets a Member pick a place: the Places UI Kit. It is Google's own list and details, drawn by Google inside our page, and it tells our code which place was picked (the `gmp-select` event gives the place ID), so Save works. Google's service terms (section 15.1) expressly allow it in an app that also has a non-Google map. Its Essentials requests and the map in the sheet fit inside Google's monthly free usage at demo scale. Place IDs are the one piece of Places data Google lets an app keep indefinitely, so a saved Google place survives without us storing anything else of Google's.

It also stays inside Utsavvy and looks like part of it, which is what Sah-Nikhil asked for: "a PWA style web applet in the app itself, without making it look shabby or like a ripoff."

The price is setup: a Google Cloud project with a billing account (a card on file, even though demo use costs nothing) and a browser key with limits. [docs/setup/google-cloud.md](../setup/google-cloud.md) has the steps.

## Considered options

Each of these was weighed with Sah-Nikhil; the first four were his ideas or his questions.

- **Places results in the Chat, with shortlisting putting them on our map** (Sah-Nikhil, 2026-10-21). Rejected under Google's terms: Places content may not be shown with or near a non-Google map, and only place IDs may be stored. A Marker from Places geometry, or from geocoding an address Places returned, would still be Google content on MapLibre. The Chat history is stored and shared, which Places content isn't allowed to be.
- **Google Maps or Google Search shown inside Utsavvy as a web page, like a PWA applet** (Sah-Nikhil, 2026-10-21 and 2026-10-22). Not possible in a browser: `google.com/maps` and `google.com/search` both send `X-Frame-Options: SAMEORIGIN` (checked 2026-10-21 and again 2026-10-22), which tells every browser to refuse to show them inside another site. Making Utsavvy an installable PWA doesn't change that, because a PWA is still our website running in the browser, just in its own window. Only a native app's built-in browser could show Google's page, and a native app is after v1 ([Ideas discussion #70](https://github.com/Sah-Nikhil/Utsavvy/discussions/70)).
- **The "Places" box from a Google Search results page** (Sah-Nikhil, 2026-10-22). That box is Google's places data, the same data the UI Kit shows. The search page itself can't be framed (above), and Google's embeddable search (Programmable Search) can't do it either: new engines search at most 50 chosen sites, and its JSON API is closed to new customers. The UI Kit with Google's map beside it is how we get that box's look and content inside Utsavvy. The ordinary web results under the box (an Instagram profile, a directory page) are what the Chat's web search already gives, as cited links.
- **Open Google Maps, then share the place back** (offered 2026-10-22). Needs no key or billing, but Members leave Utsavvy to browse and come back with a link: pasted by hand on a desktop or an iPhone, or shared straight into Utsavvy only on Android with the PWA installed (Web Share Target). Rejected as the main flow because it leaves the app; kept as the card's "Open in Google Maps" button.
- **Maps Embed API in search mode.** Free and allowed in an isolated sheet, but the iframe belongs to Google's site and tells our page nothing, so a Member couldn't save the place they found. Kept as the fallback if the UI Kit spike fails.
- **Reading Google results through Serper and storing them.** Serper's results are collected from Google with no licence from Google, and Google's terms allow keeping only place IDs. Serper stays what vendors.md made it: a way to find a Vendor's own website, keeping only the URL.

## Consequences

- A Google place is not a Vendor. It has no Listed price, Marker, checklist link or Quote, and it never feeds the reference table.
- Any Vendor Marker comes from Geoapify geocoding the address the Vendor publishes on its own site (or a human-checked profile address in the starter set), or from a Member dropping one from their own knowledge. Never from Google.
- Google's map appears only inside the sheet. The sheet is opaque and full-screen, and the workspace behind it is inert, so MapLibre can't be seen while it is open: the two maps never share a screen, and nothing links them. This matters because section 15.1's permission covers the UI Kit; the separately loaded Google map falls under the general rule against Google maps "with or near" a non-Google map, which gives same-screen and linked maps as its examples and doesn't address separate screens of one app. Separate screens with no link is the narrow reading. If Google ever objects, the sheet drops the map and keeps the list, which is the 2026-10-21 design.
- Result markers on Google's map are Google's Advanced Markers, which need a Map ID (`NEXT_PUBLIC_GOOGLE_MAPS_MAP_ID`). Place locations stay in the browser for the open sheet only.
- The UI Kit components are still Experimental (pre-GA), so S20 starts with a spike. The app depends on a billed Google Cloud project and a browser key (`NEXT_PUBLIC_GOOGLE_MAPS_API_KEY`) restricted by website and API, with daily caps where the console offers them so a copied key can't run up a bill. Each sheet open is one map load (Dynamic Maps) and each search or details view one Places UI Kit Query, each with 10,000 free a month.
- Google key restrictions can't match `utsavvy-*.vercel.app` (no wildcard mid-hostname), and `*.vercel.app` would trust every Vercel site, so the key allows only the production URL, `localhost:3000` and S20's own branch preview. Other previews show "Google places can't load right now."; the browser tests stub Google.
- The site's Content Security Policy must allow Google Maps JavaScript, including the map's tiles, and the site must send a referrer (the browser default, `strict-origin-when-cross-origin`) for the website restriction to work.
